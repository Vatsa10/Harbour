# Phase 2 — ERPNext

**Scope note:** this report covers **ERPNext only** (v16-era checkout, a customized fork — see §6). Odoo is still being cloned and gets its own report. ever-gauzy and idurar are covered in `docs/erp-scout/PHASE1-GAUZY-IDURAR.md`.

Evidence base: seven deep scout scans (spine/controllers, GL core, AR/AP billing, tax & pricing, stock, manufacturing, selling/buying, assets/maintenance/support, projects/CRM, integrations/portal) plus adversarial audits of each. **Where a scan and its audit conflicted, the audit's finding is the one recorded here**, and the disagreement is flagged inline as `[audit]`. All paths are repo-relative to the ERPNext checkout.

---

## 1. Verdict

**World-class at.** ERPNext's genuine achievement is that it encodes fifteen years of accounting and inventory scar tissue as *executable invariants*, funnelled through single choke points that cannot be bypassed. Every money-touching document in the system builds a list of GL dicts and hands it to one function (`erpnext/accounts/general_ledger.py:34`), which runs a fixed pipeline — budget check, dimension offsetting, closed-period gate, cost-center allocation, merge, negative-normalisation, payment-ledger mirroring, balance check with round-off, freeze gate, PCV gate — so no voucher type can invent its own posting rules. Every stock movement writes an append-only Stock Ledger Entry from which Bin, valuation and GL are all derived, so COGS is never `rate × qty` but always the delta in total stock value. Party outstanding is never a mutated counter but a two-CTE recomputation over an append-only signed subledger. Cancellation never deletes; it writes contra entries. On top of that sit three genuinely excellent generic engines: the declarative status/quantity-propagation engine (`erpnext/controllers/status_updater.py`) that makes "how does an order know it is fully delivered" a config table rather than per-doctype code; the tax engine's inclusive-price back-solve and error-diffusion rounding (`erpnext/controllers/taxes_and_totals.py`); and the business-hours SLA engine that attaches to any doctype (`erpnext/support/doctype/service_level_agreement/service_level_agreement.py`). The breadth is real too — depreciation across four methods and multiple finance books, MRP with sub-assembly netting, finite-capacity job-card scheduling, landed costing, subcontracting in both directions, withholding tax as its own reconciling subledger.

**Weak at.** Structurally, ERPNext is a seven-level single-inheritance chain (`Document → StatusUpdater → TransactionBase → AccountsController → StockController → SubcontractingController → Buying/SellingController → concrete doctype`) with no interface boundaries, so a Quotation carries stock, subcontracting and GL machinery it can never use, and behaviour is selected by hardcoded `if self.doctype in [...]` lists scattered across many files. `validate()` recomputes the entire document — item details, pricing rules, every tax, party details — on every save, up to three full passes; it is idempotent by brute force, not by design. Business rules live in Singles settings read ad hoc deep inside math (`round_row_wise_tax`, `enable_immutable_ledger`, `use_legacy_budget_controller`, ~30 more), so a document's behaviour is not determined by the document, and there is no record of which rule version produced which ledger row. Cross-cutting behaviour is threaded through global `frappe.flags`. Status is denormalised into strings written by `db_set` from dozens of call sites and drifts. Accounting dimensions mutate the database schema at runtime via Custom Fields on GL Entry and ~60 other doctypes. Reposting mutates *submitted* documents (rewriting rates on child rows), which quietly undermines the immutability the ledger design otherwise buys. And the codebase is mid-refactor in at least four places, shipping two implementations simultaneously behind settings flags.

## 3. THE BUSINESS RULES WORTH INHERITING

Each rule is stated precisely enough to reimplement. Source path given. `[audit]` marks where the adversarial audit corrected or qualified the scan.

### 3.1 Ledger & posting invariants

| Rule | Statement | Source |
|---|---|---|
| Single posting choke point | All GL creation goes through one function running a fixed, load-bearing order: budget → dimension offsetting → period validation → disabled-account check → cost-center allocation split → merge → negative-toggle → payment-ledger mirror → balance/round-off → freeze gate → PCV gate → insert. Period Closing Voucher is excluded from budget, PLE and allocation. | `accounts/general_ledger.py:34` |
| Minimum two lines | A posting whose surviving line count after merge and zero-drop is < 2 throws. | `accounts/general_ledger.py` |
| Two-tier balance tolerance | Debit/credit difference allowance is `5/10^precision` for **Journal Entry and Payment Entry** (manually entered) but a **flat 0.5** for all derived vouchers (invoices, stock entries). Diff above allowance throws; diff at/above `1/10^precision` inserts a round-off GL line on `Company.round_off_account`, or `round_off_for_opening` (mandatory) when any line is an opening entry. Balance is **re-checked after** the round-off insert. | `accounts/general_ledger.py:397,451,475` |
| Merge key | Lines collapse only when *all* of: account, cost_center, party, party_type, voucher_detail_no, against_voucher(+type), project, finance_book, voucher_no, advance_voucher(+type), **plus every active accounting dimension** are equal. Rows flagged `_skip_merge` bypass. Zero debit+credit rows are then dropped — except Exchange-Gain-Or-Loss journals, which may legitimately carry zero-value lines. | `accounts/general_ledger.py:226,282,302` |
| No negative amounts stored | A negative debit becomes a positive credit and vice versa, per currency triple. `post_net_value` rows net debit against credit so only one side survives. Both-negative-and-equal is flipped first as a special case. | `accounts/general_ledger.py:316` |
| Reverse, never delete | `GLEntry.on_cancel` throws outright. Cancellation re-reads the voucher's live entries `FOR UPDATE`, delinks PLE, marks originals `is_cancelled=1`, inserts swapped mirrors. With `enable_immutable_ledger`, originals are untouched and the reversal posts **live, dated today** — the legally correct behaviour in many jurisdictions. `partial_cancel=True` narrows reversal to rows sharing a `voucher_detail_no`. | `accounts/general_ledger.py:607` |
| Party subledger sign convention | Every GL line hitting a Receivable/Payable account mirrors into a Payment Ledger Entry with `amount = debit − credit` for Receivable, `credit − debit` for Payable, negated on cancel. | `accounts/utils.py:2024` |
| Outstanding is derived, never incremented | Two CTEs — one summing rows where `voucher_no` matches, one summing rows where `against_voucher_no` matches — left-joined on account+voucher+party. `paid = invoice_amount − outstanding`. Result written back onto the invoice. | `accounts/utils.py:2301` |
| Party currency lock | A party's currency is permanently fixed to that of its first GL entry per company. | `accounts/party.py:608` |
| Four amount pairs per line | Account currency, company currency, transaction currency, reporting currency — all stored on the GL line, never reconverted at report time. Missing reporting rate hard-throws. | `accounts/doctype/gl_entry/gl_entry.py` |
| Three orthogonal period gates | (1) Accounting Period + Closed Document table blocks **creation and cancellation** of listed doctypes, bypassable by `exempted_role`. (2) `Company.accounts_frozen_till_date` — **Administrator is explicitly denied the bypass**. (3) Period Closing Voucher blocks any posting dated ≤ MAX(period_end_date), and blocks all opening entries once any PCV exists. | `accounts/services/gl_validator.py:96,120,134` |
| Cost-center allocation at posting time | If a submitted Cost Center Allocation exists for (company, main CC, valid_from ≤ posting_date), each line explodes into one line per child at `amount × pct/100`. Round-off lines are re-pointed, not split. Percentages must total exactly 100; `valid_from` must be after the last GL entry against the main CC; no chaining (a CC used as a child cannot be a main). | `accounts/general_ledger.py:156`, `doctype/cost_center_allocation/` |
| Deferred schedule derives from the ledger | Next slice starts the **day after** the last posted entry (GL *or* Journal Entry Account) against that item's deferred account — making the process idempotent and restartable. End clips to month-end / service_end / service_stop / posting_date. The **final slice books `net_amount − already_booked`**, absorbing all accumulated rounding exactly once. If books are frozen past the slice end, GL posts at the month-end after the freeze date while the schedule cursor still advances. | `accounts/deferred_revenue.py:149,225,306,424` |

### 3.2 Tax & totals

| Rule | Statement | Source |
|---|---|---|
| Inclusive tax as slope+intercept | Model each tax as `tax = slope × net + intercept`; accumulate slope and intercept across the entire tax table (including On-Previous-Row chains and per-quantity charges); then back-solve `net = (amount − Σintercept) / (1 + Σslope)`. This is the correct general solution — far better than the usual `amount/(1+rate)` hack, which breaks on chained and per-qty taxes. | `controllers/taxes_and_totals.py:308-393` |
| Error diffusion for per-item breakup | Each item's tax share is the **delta of a running cumulative total rounded at each step**, so the per-item breakup always sums exactly to `base_tax_amount_after_discount_amount`. Same trick for taxable amount. | `taxes_and_totals.py:677-715` |
| Residual on last row, with a ceiling | Leftover difference is pushed onto the last breakup row; tolerance 0.5, or 1 for zero-precision currencies (JPY/KRW); anything larger **throws** rather than silently mismatching. | `taxes_and_totals.py:525-577` |
| Fixed charges don't shrink with a discount | When discounting on Grand Total, `Actual` and `On Item Quantity` charges — and any percentage tax chained onto them — are excluded from the discountable base. | `taxes_and_totals.py:959-1000` |
| Two-pass discount | Distribute header discount proportional to item `net_amount`, track expected-vs-actual running totals, inject the rounding difference into the current row while decreasing that row's `distributed_discount_amount` by the same amount, then **re-run the entire calculation** with `discount_amount_applied=True`. | `taxes_and_totals.py:901-957` |
| Rate/margin/discount reconciliation | If the user types a rate **above** price_list_rate, convert the delta into an Amount margin and clear the discount; if **below**, convert into a discount_amount and clear the margin. Pricing rules always win. | `taxes_and_totals.py:166-223` |
| Inclusive-tax validity | An inclusive `On Previous Row Total` tax requires every preceding row to also be inclusive. `Actual` and `Valuation` charges can never be inclusive. `row_id` only for previous-row types, never row 1, never ≥ own idx. | `accounts/services/taxes.py:239-261,298-322` |
| Tax Rule resolution | Blank field = wildcard. Score each rule by **count of non-blank keys matched**; specificity wins, `priority` only breaks ties. Customer/supplier groups expand to nested-set ancestors. At save time, throw `ConflictingTaxRule` if an identical filter set with overlapping dates has equal priority. `[audit]` — conflict detection only inspects the *first* overlapping rule, so deeper conflicts slip through; fix that in a reimplementation. | `accounts/doctype/tax_rule/tax_rule.py:120,136,222` |
| Explicit exemption ≠ zero | A `NOT_APPLICABLE_TAX` sentinel distinguishes "exempt" from "0%". Item Tax Templates with validity/max-net-rate bands are preferred over unbounded ones, sorted `valid_from` desc, then matched on tax_category; an already-valid template on the row is never changed. | `stock/get_item_details.py:872-939` |
| Withholding thresholds | Once **any** Settled withholding entry exists in the period, the threshold is treated as permanently crossed and deliberately not re-checked (the code cites conflicting tax rulings as the reason). Remaining threshold = cumulative_threshold − YTD Under-Withheld, further capped by single_threshold unless disabled. Under tax-on-excess regimes only the amount above the threshold is taxed, and the exempt slice is recorded as its own entry with `under_withheld_reason='Threshold Exemption'` so it is auditable and not double-counted. | `accounts/doctype/tax_withholding_entry/tax_withholding_entry.py:601-634` |

### 3.3 Status & quantity propagation

| Rule | Statement | Source |
|---|---|---|
| Declarative propagation config | Each doctype declares a `status_updater` list: source_dt, target_dt, join_field, source_field, target_field, target_ref_field, target_parent_dt/field, percent_join_field, status_field, keyword, overflow_type, extra_cond, and optionally `second_source_dt` (a second contributing doctype — e.g. a Sales Invoice with `update_stock=1` also delivers a Sales Order line). | `controllers/status_updater.py` |
| Recompute, never increment | On submit/cancel the engine **re-SUMs all sibling submitted rows** into the target field. The `cond` fragment ORs the current doc in on submit and ANDs it out on cancel, so one query serves both directions. This is what makes cancel and amend correct for free. | `status_updater.py:534-604` |
| Percentage formula | `pct = Σ min(|done|, |ordered|) / Σ |ordered| × 100`, rounded to 6 dp. The `min()` cap is what stops over-delivery producing >100%. Thresholds: `<0.001` → "Not X", `≥99.999999` → "Fully X", else "Partly X". | `status_updater.py:606-640` |
| Allowance ladder | Overflow% = `(done − ordered)/ordered × 100`. Breach iff `overflow% − allowance > 0.01`. `max_allowed = ordered × (100+allowance)/100`. Allowance resolves **item field → settings singleton** (`Item.over_delivery_receipt_allowance` → Stock Settings; `Item.over_billing_allowance` → Accounts Settings; Buying Settings for MR→PO). A designated role (`role_allowed_to_over_deliver_receive` / `role_allowed_to_over_bill`) downgrades the throw to a warning. `no_allowance: 1` disables tolerance entirely. Internal customer/supplier amount overflows are silently exempt. The error message must name both `max_allowed` and `reduce_by`. | `status_updater.py:419-467,750-816` |
| Status as data | The whole status vocabulary is one table of (status, predicate) pairs, scanned **reversed so later entries win**. Manual states (Closed, On Hold, Stopped, Lost) are expressed as self-referential conditions so they survive recomputation. | `status_updater.py:21-179` |
| Billable-after-return | `billable_qty = min(qty, max(qty − returned_qty, delivered_qty))`. One line; it is the whole answer to "what can still be invoiced after a partial return and re-delivery". | `selling/doctype/sales_order/mapper.py:424-428` |
| DN billing percentage | Delivery Note billing % is `max(amount-basis, qty-basis)` per row — amount basis capped at delivered amount, qty basis derived from invoiced qty — and once the whole DN is returned it reverts to the original amount basis. This is a scar from rate-drop-on-invoice bugs. | `controllers/stock_controller.py:333-369` |
| Per-installment overdue | An invoice is Overdue when `(total − outstanding) < Σ payment-schedule installments whose due_date < today` — **not** merely when the final due date passed. POS and schedule-less invoices fall back to plain due_date. | `accounts/doctype/sales_invoice/services/status.py:96` |

### 3.4 Inventory & valuation

| Rule | Statement | Source |
|---|---|---|
| SLE is truth, Bin is cache, GL mirrors the value delta | Every movement appends an immutable SLE carrying computed running state (`qty_after_transaction`, `valuation_rate`, `stock_value`, `stock_value_difference`, `stock_queue`). Bin is a rebuildable per-(item,warehouse) cache. GL debits inventory by `stock_value_difference` and credits COGS/expense by its negative. **COGS is never `rate × qty`** — always `value_now − value_before`. | `stock/stock_ledger.py:1169-1172`, `stock/doctype/bin/bin.py` |
| FIFO/LIFO bin queue | A list of `[qty, rate]` bins. `remove_stock` returns the consumed bins so the caller derives value from the delta. **Purchase returns consume the rate-matched bin, not the queue head** (a return must give back the exact layer it took), falling back to FIFO. When the queue empties with qty left, push a **negative bin** `[-qty, rate]` so later inward stock nets against it. `add_stock` merges into the last bin at equal rate; against a negative last bin it absorbs at the new rate only if the result turns positive. | `stock/valuation.py:85-159` |
| Kill float dust | `round_off_if_near_zero(precision=7)` applied to every qty and value — without it FIFO queues accumulate 1e-13 ghost bins forever. | `stock/valuation.py:260-267` |
| Moving average fallback ladder | Inward: `rate = (old_qty×old_rate + qty×in_rate)/new_qty`. Outward with explicit rate: re-derive. Balance negative: fall back to outgoing_rate, then item rate, then price-list rate. | `stock/stock_ledger.py:1038-1226` |
| Valuation rate fallback (perpetual only) | batchwise avg from SLEs → bundle batch avg → last non-negative valuation_rate for item/warehouse excluding this voucher → `Item.valuation_rate` → `Item.standard_rate` → buying Item Price → throw with a three-option remediation message. Only throws when perpetual inventory is on. | `stock/stock_ledger.py:2145-2258` |
| Serial vs batch outward value | **Serial:** value = Σ of each serial's latest *inward* rate, resolved by `max(posting_datetime)` then `max(creation)`, excluding the current voucher. **Batch:** `batch_avg_rate = Σ stock_value_difference / Σ qty` over that batch's prior entries. | `stock/serial_batch_bundle.py:676-755,1020-1035` |
| Datetime is not a total order | Ordering everywhere is `(posting_datetime, creation)`; `creation` is the tiebreaker. Bundle creation and SLE creation are *different timelines* and the batch code carries an EXISTS subquery specifically to disambiguate them. **A reimplementation should use a monotonic ledger sequence number and delete this entire bug class.** | `stock/stock_ledger.py:1978-2019`, `serial_batch_bundle.py:906-985` |
| Reconciliation is a barrier | Stock Reconciliation sets an *absolute* balance, so future-qty propagation (`update_qty_in_future_sle`) is bounded by the next reconciliation. Its "delta" is `qty_after_transaction − previous balance`; on cancel it uses the `previous_qty_after_transaction` captured at submission. For serialized items a reconciliation is **always two SLEs** — a full outward of the current bundle, then an inward of the new one. An all-zero row emits an adjustment entry whose `stock_value_difference` is the negated cumulative value, forcing the ledger to exactly zero. | `stock/stock_ledger.py:2261-2358`, `doctype/stock_reconciliation/stock_reconciliation.py:946-984` |
| Negative-stock threshold | `diff = balance + actual_qty − reserved_stock`, compared against `max(10^-float_precision, 0.0001)`. **Reserved stock genuinely reduces what you may consume.** | `stock/stock_ledger.py:1397-1415` |
| Projected qty formula | `projected = actual + ordered + indented + planned − reserved − reserved_for_production − reserved_for_subcontract − reserved_for_production_plan`. This is the contract for every availability check in the system. | `stock/doctype/bin/bin.py:78-88` |
| Bin actual_qty source | Taken from the just-processed voucher **unless** future SLEs exist or this is a cancellation, in which case re-read from the last SLE. Three lines that encode the whole "back-dated entries make the cache wrong" rule. | `stock/doctype/bin/bin.py:261-316` |
| Intra-voucher queue order matters | If one voucher consumes the same (item, warehouse) twice under FIFO/LIFO, its SLEs must be reprocessed in background — intra-voucher queue consumption is order-dependent. | `controllers/stock_controller.py:653-679` |
| Landed cost apportionment | `charge_i = basis_i × total_charges / total_basis` (basis = qty, amount, or manual), **residue added to the last row** so the split sums exactly; re-checked within `2/10^precision` or throw. Valuation-category taxes split three ways: On-Net-Total apportioned by item_tax_rate; `Actual` with `allocate_full_amount_to_stock_items` (freight) spread across stock/asset rows only; other `Actual` spread across all rows but only the stock share capitalised. `_spread_charge_over_items` proportions by `base_net_amount`, **falls back to qty when all amounts are zero**. Non-stock rows get valuation_rate 0. | `stock/doctype/landed_cost_voucher/landed_cost_voucher.py:207-270`, `controllers/buying_controller.py:563-587` |
| Immutable masters | `has_serial_no` / `has_batch_no` / `is_stock_item` / `valuation_method` freeze once submitted transactions exist — with the single exception that FIFO→Moving Average is allowed (not the reverse). | `stock/doctype/item/item.py:1102-1145` |
| Received = accepted + rejected | `received_qty` must equal `qty + rejected_qty` at row precision; auto-filled when blank; else `QtyMismatchError`. | `controllers/buying_controller.py:735-748` |
| Dry-run ledger preview | Compute the GL and SLE postings, show them, then `frappe.db.rollback()`. Steal this verbatim — it is the single best UX idea in the codebase. | `controllers/stock_controller.py:618-650` |
| Putaway allocation | `free_space = stock_capacity − current balance`; rules sorted `(priority asc, −free_space)`; return `(at_capacity, rules)` so the caller can distinguish "no rules" from "rules but full"; allocation floors to whole numbers where the UOM demands. | `stock/doctype/putaway_rule/putaway_rule.py:244-272` |
| Picking nets in-flight picks | Already-picked qty from **other open pick lists** is subtracted before allocation — the invariant that prevents double allocation. | `stock/doctype/pick_list/pick_list.py:1157-1175` |
| Item price precedence | `ORDER BY (valid_from IS NOT NULL), valid_from DESC, batch DESC, uom DESC, party DESC, name DESC` — the final `name` tiebreak exists because MariaDB and Postgres otherwise picked different rows. | `stock/get_item_details.py:1292-1345` |

### 3.5 Manufacturing & MRP

| Rule | Statement | Source |
|---|---|---|

## 4. The Frappe dependency

### What the framework actually provides

| Frappe capability | What ERPNext gets from it | Replacement cost if you don't adopt it |
|---|---|---|
| DocType metadata (schema-as-data) | The reason **one** 1770-line `AccountsController` drives Quotations, Orders, Invoices and Delivery Notes: controllers branch on `self.meta.get_field(x)` / `has_field(x)` at runtime. | High — this is the single deepest coupling. Without runtime-introspectable schema, generic controllers become per-doctype code. |
| Submittable lifecycle (docstatus 0/1/2) | Immutability, amend chains (`amended_from`), `no_copy`, `allow_on_submit`, and the entire cancel-as-reversal model. Every aggregate query filters `docstatus == 1`. | Medium — easy to model explicitly, and you'd model it *better* (a real state machine). |
| Child tables with stable row names | Cross-document links are child-row-to-child-row (`quotation_item`, `so_detail`, `voucher_detail_no`). Partial-fulfilment tracking, SLE→line traceability, landed-cost apportionment and repost dependency chains all key off child row names. | Low — ordinary FK rows. |
| Custom Field / Property Setter (runtime schema mutation) | Accounting dimensions physically add columns to GL Entry and ~60 doctypes; SLA injects ~12 tracking fields into any target doctype; regional setup installs country fields. | Low, and **you should not replicate it** (§6). |
| `doc.precision(fieldname)` | The entire tax and valuation rounding system resolves precision from DocField + currency settings. | Medium — needs an explicit money/precision model, which is an improvement. |
| `frappe.qb` (PyPika) + recursive CTEs + `FOR UPDATE` | Every roll-up, tree traversal, outstanding query, and the ledger walker's row locking. | Low — any query builder. |
| Singles (settings doctypes) | ~30 toggles that change posting and valuation math. | Low mechanically, but see §6 — this is a modelling problem, not a framework one. |
| `frappe.safe_eval` | `status_map` conditions, pricing-rule conditions, scorecard formulas and weighting functions, quality-inspection acceptance formulas. | Low — replace with a typed expression language. |
| Background jobs + scheduler | Reposting, BOM mass recost, POS consolidation, bulk transactions, deferred booking, dunning/expiry jobs. | Low — any job runner. |
| `hooks.py` registry | doc_events, scheduler_events, regional_overrides, accounting_dimension_doctypes, auto_cancel_exempted_doctypes, `erpnext_taxable_base_resolvers`, `fields_for_group_similar_items`. | Low — plugin registry. |
| `get_mapped_doc` | Every document-to-document hop (quote→order→DN/SI/PO, WO→Stock Entry, SCO→SCR, Lead→Customer) is a declarative field_map + per-row condition. | Medium — worth reimplementing deliberately; the pattern is excellent. |
| `patches.txt` migration runner | 516 lines, twelve version folders, pre-/post-schema-sync phases. | Low — and you should use a real migration tool with a dependency graph and down-migrations. |
| Desk UI, portal, permissions, print formats, reports | Enormous surface ERPNext gets free. | Very high if you need it; low if you're building your own front end anyway. |

### The strategic question

Adopting a metadata/doctype-driven engine buys you: generic controllers over many document types, free CRUD/list/form UI, runtime extensibility for customers, and a permission model. It costs you: no static types, no compile-time verification of any business rule, business logic expressed as eval'd strings, schema mutation as a supported operation, and a codebase where the *shape* of a document is determined at runtime so nothing can be statically analysed. ERPNext's weaknesses list is almost entirely downstream of that trade.

### Recommendation

**Do not adopt a metadata-driven document engine. Adopt the two ideas underneath it, statically.**

Reasoning:

1. **The value ERPNext extracts from schema-as-data is narrow.** It is essentially "one controller can serve ten doctypes." You get the same leverage from composition — a `TaxableDocument`, `StockAffecting`, `PartyLedgerAffecting` set of typed mixins/protocols — without giving up the type system. The seven-level inheritance chain plus `if self.doctype in [...]` lists is *worse* than composition, not better, and it exists because inheritance was the only tool the metadata model offered.

2. **The rules worth inheriting are all pure functions.** Read §3 again: inclusive-tax back-solve, FIFO bin queues, pro-rata depreciation, MRP netting, percentage propagation, business-hours walks. None of them need runtime schema. ERPNext's own best module (`stock/valuation.py`, 267 lines, zero Frappe imports) proves the point — it is the most portable file in the repo *because* it escaped the framework.

3. **Runtime schema mutation is the single most damaging pattern here** and it is a direct consequence of the metadata engine. Accounting dimensions add real columns to GL Entry and ~60 doctypes; SLA rewrites the schema of any doctype it attaches to and `reset_field_properties` overwrites existing fields without asking. Model dimensions as a proper dimension-value table (or JSONB with generated columns) and the problem disappears.

4. **You are not competing on customer-customisable schema.** ERPNext needs it because it ships one binary to thousands of self-hosted sites with no developers. If your extensibility story is a typed plugin API plus a small set of user-defined dimension/attribute tables, you carry none of this cost.

5. **What to take instead:** (a) *declarative config where the config is data but the interpreter is typed code* — the `status_updater` config list is the right idea; its string-formatted SQL is not. Express it as typed records interpreted by a compiled engine. (b) *Named extension points* — `@allow_regional`, `erpnext_taxable_base_resolvers`, `get_matching_queries` are good; a plugin registry keyed by explicit interfaces, not dotted-path strings resolved at call time via a thread-local flag. (c) *One canonical line-item resolver* — the concept behind `get_item_details.py` is right; its 1889-line god-module shape is not.

If you are already committed to a metadata engine for other reasons, the mitigations that matter most are: forbid runtime schema mutation, replace `safe_eval` with a typed expression AST, and version the settings that change posting semantics so a ledger row records which rule produced it.

## 6. Traps, tech debt and correctness pitfalls not to repeat

**The back-dating trap — decide this on day one.** Allowing back-dated stock and accounting entries is what forces the entire Repost Item Valuation subsystem into existence: queueing, gzipped checkpointing, resume-on-timeout, dedup, coverage-skipping, parallel workers with per-item exclusion, deadlock retry, failure emails. In practice reposts sit Queued for hours, block period closing (`check_pending_reposting`), and leave reports showing stale valuation. The root cause is that valuation state is denormalised *into* the ledger (`stock_queue` JSON, `qty_after_transaction`, `valuation_rate` on every row), so any historical change invalidates every later row. **Design choice:** either forbid back-dating and make correction an explicit forward-dated adjustment document, or store only the movement on the SLE and keep valuation as a separately rebuildable projection. Do not discover this late.

**Datetime is not a total order.** Correctness throughout stock depends on `(posting_datetime, creation)` tiebreaks, and at least one place needs an `EXISTS` subquery because "bundle creation and SLE creation are different timelines" (`serial_batch_bundle.py:906-985`). Use a monotonic ledger sequence number and delete the bug class.

**Concurrency correctness is database-specific.** This checkout carries MariaDB-gap-lock vs Postgres-advisory-lock branches in at least three places (`stock_ledger.py:306-331`, `serial_batch_bundle.py`, `pick_list.py:600-611`), plus `SELECT rows FOR UPDATE` instead of `COUNT` because Postgres rejects `FOR UPDATE` with aggregates (`appointment.py:368-390`), plus explicit MariaDB/Postgres divergence comments in the outstanding CTE (`accounts/utils.py:2301`) and an Item Price `ORDER BY name` tiebreak added because the two engines picked different rows. **Pick one database.**

**Fork warning.** This checkout is a **customized ERPNext fork**, not upstream. It adds: a `Standard Cost` valuation method whose whole point is that back-dated entries need no repost (`stock_ledger.py:57-101,1015-1037`), Postgres advisory-lock gates, and a `services/` layer extracted out of the big controllers (`stock/services/`, `accounts/services/`, `manufacturing/.../services/`). Do not assume behaviour matches upstream ERPNext docs.

**Known-broken or dead code found by the audits.** Treat these as evidence of the class of defect the architecture invites, not as a bug list to fix:

- `Issue.split_issue` sets `replicated_issue.resolution_by` — a field that no longer exists (renamed `sla_resolution_by`). Silent no-op. (`support/doctype/issue/issue.py:120-141`)
- `get_expected_time_for` is an **unbounded `while` loop** — an SLA whose support-day list never matches, or a holiday list covering the horizon, spins forever. Also contains a no-op `pass` branch. (`service_level_agreement.py:663-699`)
- `calculate_first_response_time` ignores the Holiday List entirely (only consults support weekdays), so the reported first-response time and the `response_by` deadline are computed on **different calendars**; it deliberately returns `1.0` instead of `0` to work around a reset elsewhere. (`issue.py:320-383`)
- `Project.set_consumed_material_cost` is **never called** from `update_costing` — so the material leg of gross margin is silently zero unless something else populates it. (`projects/doctype/project/project.py`)
- Two contradictory periodicity day-tables in the same file: Quarterly=91/Half-Yearly=182 in one check, 90/180 in another — the same contract can pass one and fail the other. (`maintenance_schedule.py:74,206`)
- Maintenance visit date spacing uses a float `add_by` fed to `add_days`, and the holiday shift only moves **backward** with an iteration cap of `len(holidays)` — a visit can land before the contract start or on a holiday anyway.
- `get_written_down_value_rate` can divide by zero `pending_years`, and `math.pow` of a negative ratio raises. (`asset.py:1030-1044`)
- `calculate_next_due_date`'s end-date test is `... or next_due_date`, so passing a `next_due_date` in always blanks it. (`asset_maintenance.py:836-841`)
- `_adjust_against_old_entries` uses `for/else` that throws whenever the loop completes without `break` — **including when amounts matched exactly on the last entry**. (`tax_withholding_entry.py`)
- `process_gl_map` runs **twice** for Payment Entry (once in `PaymentEntry.make_gl_entries`, again inside `make_gl_entries`), so merge and negative-toggle execute twice.
- `get_dimension_fieldname` returns `None` for any dimension that is not Cost Center or Project — an unfinished helper. (`accounting_dimension.py:364`)
- `Opportunity.map_fields()` copies any same-named field from the source party doctype with a bare `try/except: continue` — a silent data-corruption vector.
- Coupon usage is a non-atomic read-modify-write on a `used` counter — racy under concurrent checkout. (`pricing_rule/utils.py:761-775`)
- Webhook signature comparison is **not constant-time**, and the `erpnext.erpnext_integrations.connectors.*` package the helper addresses **no longer exists on disk**. (`erpnext_integrations/utils.py`)
- `Tax Rule` conflict detection inspects only the first overlapping rule. (`tax_rule.py:136`)
- `validate_parent_project_dates` is skipped entirely under `frappe.in_test` — a core invariant the test suite cannot exercise. (`projects/doctype/task/task.py:105-153`)
- `adjust_rounding_in_item_wise_tax_details` carries a literal `# TODO: fix rounding difference issues` and tolerates 0.5 of unexplained difference; remainders are dumped on "the last row" in at least four separate places.
- POS merge-log credit-note linkage has an explicit TODO: a return may span multiple already-consolidated invoices, but only one `return_against` is stored.
- `Quality Management` is close to inert: `QualityGoal.validate` is `pass`, `QualityMeeting` is `pass`, Non Conformance has no controller, and `quality_review.review()` compares a Literal day-of-month **string** against an int day and only covers 1–30, so the 31st never fires.
- `asset_capitalization.py` still carries commented-out code and a `get_gl_entries` signature whose `default_expense_account`/`default_cost_center` parameters are accepted and ignored.

**Performance landmines to design out.** `validate_balance_type` runs `SUM(debit)−SUM(credit)` over the **entire account** on every GL Entry insert when `balance_must_be` is set — O(ledger) per line. Fuzzy party matching loads every Customer, Supplier and Employee name into memory **per statement line**. Party Specific Item filtering loads all rules globally on every item autocomplete keystroke. Project Summary issues three count queries per project row. `financial_statements.get_data` issues one GL query per root account and materialises every entry in Python before bucketing (only survivable because of the PCV short-circuit). Quotation ordered-status does an `frappe.db.exists` per row.

**Semantic gaps that will bite a serious ERP.** No standard cost with purchase-price/usage/efficiency variance accounting. No time-phased MRP — netting is a single-bucket `projected_qty` check, not a period-by-period planned-order schedule with lead-time offsetting. No capacity requirements planning or load report from the plan; no feedback loop from job-card delays back to work-order dates. No critical path, slack or resource levelling in projects; rescheduling is forward-only, single-hop, Open-tasks-only, one project. No WIP/accrued revenue — project gross margin uses *billed* as revenue, so delivered-but-unbilled work reports as pure loss. No usage-based/metered subscription billing and no mid-period plan-change proration. No dunning automation (no scheduled escalation, no configurable multi-level policy). Backflush mode is a global setting with only a per-BOM override, not per-item or per-warehouse. Asset `status` is one flat Select mixing lifecycle, depreciation state, disposal and operational state — an asset cannot be both partially depreciated and in maintenance. Regional coverage is thin (UAE, Italy, US real; AU/ZA/TR setup-only) and India/GST had to move to a separate app — evidence that the right localisation boundary is a **plugin, not a folder**.

## 7. Open questions for the owner

1. **Back-dating.** Do we allow back-dated stock and accounting postings at all? If yes, we are committing to a repost subsystem on day one (§6). If no, what is the correction UX — a forward-dated adjustment document? This is the single highest-leverage decision in the whole report.
2. **Metadata engine.** Do you accept the §4 recommendation (typed composition + typed declarative config, no runtime schema)? If not, what is driving the need for customer-defined schema, and can it be met by a bounded dimension/attribute model instead?
3. **Database.** One engine, or portability? ERPNext pays a permanent tax for MariaDB+Postgres (§6). Picking one removes an entire class of concurrency and ordering bugs.
4. **Valuation methods at v1.** FIFO only, or FIFO + Moving Average + Standard Cost? Standard Cost is the method that makes back-dating cheap (this fork added it for exactly that reason) — but it needs variance accounting, which ERPNext does not have.
5. **Immutable ledger mode.** Backdated `is_cancelled` flip, or current-period live reversal? This is a jurisdictional legal question, not a preference — which markets are in scope at v1?
6. **Accounting dimensions.** How many analytic axes, and are they known at design time? If bounded and known, model them as real columns; if user-defined, a dimension-value table with a bounded axis count. Either way, not runtime Custom Fields.
7. **Serial/batch at v1.** Is full serial-level valuation (latest inward rate per serial) in scope, or batch-level only? ERPNext's dual legacy representation exists because it retrofitted the good model over the bad one — decide once.
8. **Manufacturing depth.** Discrete only, or process manufacturing (co-products, yields)? Secondary Items with `cost_allocation_per` is the right shape for co-products, but adds an invariant (allocation totals 100%) to every BOM.
9. **Subcontracting direction.** Outbound only, or also inbound (being the job-worker, with customer-supplied materials in a customer-owned warehouse)? Most open ERPs omit inbound entirely; ERPNext has it and it is a differentiator.
10. **CRM boundary.** ERPNext is actively separating CRM into a separate product (Frappe CRM), with `crm_deal` custom fields stamped onto Quotation and Customer as the integration seam. Where exactly is our line? Concretely: Quotation's `quotation_to` supporting Lead/Prospect/Deal, credit-limit policy (customer attribute but the check needs ERP outstanding), party address/contact ownership, dunning/collections, Sales Person hierarchy and commission (commission math hits GL and payroll; sales-org structure is CRM-flavoured), and Contract — which is filed under CRM but links to Sales Order, Purchase Order and Project and is genuinely ERP.
11. **Portal scope.** Read-only customer/supplier portal, or does the supplier RFQ **write** path (`templates/pages/rfq.py`) make v1? Supplier collaboration is a real differentiator most open ERPs lack.
12. **Localisation architecture.** Plugin apps per country from day one, or a folder plus a country registry? ERPNext's own India/GST extraction answers this, but it costs a stable plugin API up front.
13. **Settings-as-business-rules.** Are we willing to make posting semantics fully document-determined (no global toggles that change math), accepting that some flexibility moves to per-company configuration recorded *on the transaction*?
14. **Migration/repair strategy.** ERPNext's best patches replay production service code to repair data rather than duplicating SQL — do we commit to that discipline, with a real migration tool (dependency graph, down-migrations) rather than an append-only list?

## 1. HOW TO USE THIS DOCUMENT

### 1.1 Relationship to the strategy plan

`ERP-MVP-PLAN.md` decides **what and why**. This document decides **how and in what order**. Where this document appears to disagree with the plan, the plan wins and the disagreement is recorded in §9 as an open item against the plan section that owns it — never resolved silently inline. That is the failure mode §2 of the plan exists to prevent.

This document does not restate strategy. It cites it: `§3.4` means `ERP-MVP-PLAN.md §3.4`. `D5` means a §9.1 day-one decision. `R7` means a §9.2 master-ranking risk. `L3`, `T16`, `V6`, `M8`, `A5`, `N14`, `J5`, `G3`, `P2`, `S2` are §6 business rules. `[VERIFY] qNN` is a §5.5 statutory question with no answer yet.

### 1.2 The rule that governs every row in this document

**No work item ships without its acceptance test.** Not "is tested" — *has a named test file, in CI, that fails the build.* The column is a command plus the assertion that must hold. A work item whose acceptance criterion cannot be written as a command is not small enough to be a work item and must be split.

Three corollaries, each of which has a specific failure it exists to prevent:

1. **Compliance claims are tests or they are not claims.** §3.5 property 6 states it directly: *"A test asserts that a row written by the migrator produces an `audit_log` row — if that test is deleted, the compliance claim goes with it."* Every sales line in §8.4 that names a capability maps to a test id in §4. If the test does not exist, the line comes out of the deck.
2. **A silent-wrong-number rule needs a test that the naive implementation fails.** §6.1 ranks the twelve most expensive rules to get wrong, and every one of them is wrong *quietly*. So the acceptance criterion for those items is written to fail against the obvious implementation — the ₹18,000 interstate job-work challan (S3-22), the two-inclusive-taxes back-solve (S2-16), the horizon-not-today MRP compare (S3-13), the PoS-restricted invoice that must not also appear as a 17(5) reversal (S2-54). A test that only passes the correct implementation is worth ten that pass both.
3. **Deleting a test is a schema-class change.** The red suite (§5) carries an integrity guard that fails the build if any test in it is skipped, removed or renamed. The `unsafeQuery` count, the `no-constants` lint and the fixture-occurrence lint are the same mechanism applied to code.

### 1.3 Governing conflict, stated up front

The product context fixes **database-per-tenant**. The plan decides **schema-per-tenant** and labels it `[BET]` with a named reversal condition gated on Stage 0 **Q8** (§3.7, §9.1 **D4**).

**This document implements database-per-tenant**, including the connection-pooling mitigations §3.7 raised as the argument against it (S1-05). §3.7, §9.1 D4 and §7 Stage 0 Q8 must be amended in the plan before S1-04 is written. Recorded as **OI-01**. The cost of being wrong now is ~2 engineer-weeks of scaffold; the cost after migrations exist is the re-platform §9.2 R6 describes.

### 1.4 Conventions

**Item ids.** `S0-nn` Stage 0 · `S1-nn`…`S4-nn` engineering stages · `U-nn` UI screens (§6) · `RS-nn` red-suite assertions (§5) · `OI-nn` open items (§9).

**Sizes.** S ≤ 3 dev-days · M ≤ 10 · L ≤ 20 · XL > 20. Sizes are for sequencing only. §7.6 withdraws the schedule estimate and forbids restating it; this document supplies the bottom-up inputs (item count, screen count, staffing interlocks) and states no total.

**Test layers, and how each is invoked.**

| Layer | Location | Command | Rule |
|---|---|---|---|

| Property | `**.prop.test.ts` | same | fast-check; invariants stated as identities |

**Definition of done, every item:** (a) the named test exists and passes; (b) `bun run acceptance` still *runs* — red is fine, **skipped is not**; (c) any migration is a hand-edited `.sql` in `packages/db/migrations/` with a written `down` where the `up` is destructive; (d) a clean-room spec document `specs/SPEC-<domain>-<nnn>.md` exists and is referenced by id from the code (§3.12 — provenance is per rule, not per project).

### 1.5 The clean-room protocol is a build constraint, not a preamble

§3.12 operationalises R28, the one risk with no engineering remedy after the fact. Mechanically, in this repo:

- `specs/` is written by **spec authors** who read the GPL sources. `CODEOWNERS` restricts `specs/**` and `tools/oracle/**` to that group.
- **Implementers never open** `ref/erpnext`, `ref/frappe-*`, `ref/odoo`. Those trees stay in the `AI-CRM` working copy and are never vendored, submoduled or `file:`-depended by the ERP repo. CI job `licence` fails on any import resolving outside the repo root and on any GPL/AGPL/LGPL/SSPL dependency.
- CI job `provenance` fails on an exported rule in `packages/domain/src/rules/` with no `// SPEC-…` comment.
- `tools/oracle/` is the only place a reference system is named, and it names them as **digest-pinned Docker images**, never as source.

The import engine (§4 Stage 4 Track A) is the largest surface where PHASE6 §4 describes reference behaviour in enough detail to be tempting to port. It is a spec, not a source.

### 2.7 Migrations

**`drizzle-kit generate` emits SQL; the SQL is hand-edited and committed. `drizzle-kit push` is banned. Runtime `migrate()` is never called from `api` or `worker`** (D7).

```
packages/db/migrations/
├─ control/   0001_init.sql  0002_shard_map.sql …
└─ tenant/    0001_conventions.sql … 0014_sales_invoice.sql   (+ .down.sql where destructive)
```

Rules:
1. Generated SQL is always hand-edited before commit. Order within a file: tables → constraints → indexes → partitions → triggers → `GRANT`/`REVOKE`.
2. **Every tenant migration ends with the grant block** — `REVOKE UPDATE, DELETE ON gl_entry, stock_ledger_entry, payment_ledger_entry, audit_log FROM erp_app;` re-asserted idempotently, so a new table never lands ungoverned. CI job `ddl-lint` fails on a `create table` in `migrations/tenant/` with no grant statement in the same file.
3. **Forward-only by default.** A `.down.sql` is written only for a migration containing `DROP`, `ALTER … TYPE`, or a `NOT NULL` addition. `fleet:migrate --rollback` refuses a range where any member lacks one.
4. **Drift gate:** CI runs `drizzle-kit generate --name __drift` and fails if it produces any statement. The schema and the migrations cannot disagree.
5. `registry:build` reads `packages/db/src/schema/tenant/**` and emits `registry.build.json` + `registry_build_id = sha256(canonical_json)`. CI fails if the committed file differs from a fresh build. **This is what makes "metadata is a projection of code" (§3.2) mechanically true.**
6. Migrator writes go through `packages/ledger`'s audited writer (D1). A raw `INSERT` into a ledger table from `apps/migrator` is a lint failure.

### 2.8 Local development — one command

```bash
bun run dev
```

`tools/scripts/dev.ts`, idempotent, does: compose up (`postgres:17-alpine`, `pgbouncer:1.24`, `redis:7.4`, `minio`, `mailpit`) → `cp -n .env.example .env` per app, `packages/env` prints the first missing key with the line to add → `migrator control:migrate` → `migrator template:build --shard local` → `migrator tenant:provision --slug dev --tz Asia/Kolkata` → `migrator tenant:seed --fixture packages/testkit/fixtures/dev-tenant.json` → MinIO bucket → `turbo run dev --parallel` (web :3000, api :3001, pdfd :3002, worker) → banner.

**Dev goes through PgBouncer too.** Transaction-pooling semantics — no session state, no prepared-statement reuse — must be the ones developers hit, or the first bug appears in staging.

**Windows note:** Chrome/Firefox resolve `*.localhost` to 127.0.0.1 without a hosts edit; Windows does not, so `tools/scripts/hosts.ps1` adds the entries. Relevant — the team's environment is Windows.

**The dev tenant fixture is not a toy.** L10 makes a missing rule an error, so a tenant with an empty rule store cannot post one document. `dev-tenant.json` seeds: a company with **two GSTINs** (27-Maharashtra plant, 24-Gujarat depot) so intra-state, inter-state and branch-transfer paths all exist on day one; an authorised signatory with a placeholder signature per GSTIN; a default cost centre (`gl_entry.cost_center_id` is NOT NULL — D10); **six series, one of them carrying `migrated_from=1, migrated_to=842, start_ordinal=843` so the mid-year cut-over path is exercised by default**; ruleset `dev-unverified-0001`; 12 items, 3 warehouses (one `subcontractor`), 2 customers, 3 suppliers (one unregistered → RCM), a two-level BOM, 3 employees; and **one open job-work challan dispatched 11 months ago, so the §143 alarm fires on a fresh `bun run dev`**. That is the demo §8.3 leads with; it should be the default state of a developer's machine.

`migrator ruleset:publish` **refuses any ruleset whose rows carry the `dev-unverified` marker.** Dev must have rules; nothing may let those rules reach a customer.

Also: `bun run dev:reset` (deterministic — fixed UUIDv7 seeds, fixed clock offset), `dev:down`, `dev:tenant <slug>` for isolation work.

**Acceptance for the scaffold:** `git clone && bun install && bun run dev` on a machine with Docker only → a browsable tenant with a printable invoice in **< 5 minutes, no manual step**; running it twice changes nothing; `bun test` (unit) needs no services.

### 2.10 `packages/money` — specified in full, because D5 is unretrofittable

Written first. Nothing else starts until §2.10's acceptance passes (§7 Stage 1: *"a two-day job every other package imports"*).

**Scales.** `MONEY 4 · QTY 6 · UNIT_PRICE 6 · TAX_RATE 6 · FX_RATE 9 · UOM_FACTOR 9 · DEC_WORKING 12 · DEC_MAX 24`.

**Types.**
```ts
export type Money<C extends CurrencyCode = CurrencyCode> =
  { readonly [MONEY]: true; readonly u: bigint; readonly ccy: C };   // minor units, scale 1e4
export type Qty  = { readonly [QTY]: true; readonly u: bigint; readonly uom: UomCode };
export type Dec  = { readonly v: bigint; readonly s: number };        // value = v × 10^-s
export type Rounder = { readonly mode: RoundingMode; readonly rulesetVersionId: string };
```

Decisions, each with the failure it prevents:

- **Currency lives in the type parameter.** `addMoney(inr, usd)` is a compile error; the runtime `ccy` check throws `CurrencyMismatch` because the type is erased at the SQL boundary and that is exactly where a mismatch enters.
- **`Dec` is `{v, s}`, not a fixed 12-dp integer.** `add`/`sub`/`mul` are **exact** (scale grows); only `div` rounds. This is the only shape in which "compute raw, round once" (D5) is literally true.
- **`div` rounds to 12 dp `half_even`, deliberately not the statutory mode.** Applying the statutory mode at working precision *and* at commit is double rounding, and it moves the last paisa on the inclusive-tax back-solve (T2). The statutory mode applies exactly once, at `commit`. → **OI-04**, an engineering ratification, not a CA question.
- **Scale ceiling at 24, then `half_even` and strip trailing zeros.** Without it a loop over 2,000 invoice lines grows the bigint without bound.
- **`Qty` carries a `UomCode` tag**, symmetric with currency, because §3.1's three sanctioned UoM rounding deviations (M9 ceil, P1 `ROUND_CEILING` in purchase UoM, V12 down-then-half-up) are all wrong if a quantity does not know its UoM. → **OI-05**, an extension beyond the plan.
- **There is no default `Rounder`.** It is built at request/job start from `resolve('codes.rounding.mode', jurisdiction, postingDate, ruleset)` and travels on `Ctx`. A module-level mutable default is the `frappe.local` pattern §3.7 rejects, and under database-per-tenant a leaked default is a cross-tenant wrong number.
- **Drizzle custom types live in `packages/db/src/types/`**, not in `money`, so `money` stays dependency-free.

**Acceptance (S1-02):**
1. `bun test packages/money --coverage` ≥ 95% lines.
2. Property: `add` commutative, `mul` associative, `decToString(mul(a,b))` matches a BigInt-only reference to full precision; a JS-`number` computation of the same expression is asserted **different**, so the test documents the overflow it exists to prevent.
3. Property: `sumMoney(allocate(total, weights, r)) === total` **exactly**, 10⁴ cases including negatives, zeros and single-element weights; no element deviates from its ideal share by more than one minor unit.
4. Table-driven: every `RoundingMode` matches an oracle at the `.5` boundary in both signs.
5. `moneyFromSql('1.00005','INR')` **throws** rather than rounding silently.
6. `addMoney(inr, usd as any)` throws at runtime and does not compile without the cast (`test-d`).
7. `dependency-cruiser` fails on any import out of `packages/money`.
8. `grep -rn "number" packages/money/src --include=*.ts` returns only `scale: number` and `cmp` return positions — no arithmetic.

### 3.2 Three defects found in the plan and corrected in the DDL

1. **§3.5's `create unique index on audit_log (chain_seq)` is invalid PostgreSQL** — the exact defect the plan flags two paragraphs earlier for `seq`. A unique index on a partitioned table must contain the partition key. Corrected with **`audit_chain_link`**: unpartitioned, `primary key (tenant_id, chain_seq)`, ~120 B/row. It also discharges the plan's *harder* requirement that `audit:verify` run over **detached and archived** partitions, which an index inside the partitions never could.
2. **`statutory_rule` cannot be both blanket-append-only and carry `superseded_by`.** Narrowed to exactly one legal mutation: `superseded_by`, once, null→value. Payload immutability — which the ruleset digest depends on — is unaffected.
3. **The deferred-balance dedup set breaks under `SET CONSTRAINTS … IMMEDIATE`.** §3.4 mandates the dedup and §3.8 mandates the mid-transaction flush; together they silently skip the second half of any voucher split across import batches. `erp.gl_flush_balance_assertions()` clears the set as part of the flush — two lines in the import loop, not one.

### 3.4 Three acceptance criteria that cannot live in the database

1. **Numbering concurrency (D2).** `erp.allocate_doc_no` raises `55P03` on contention; the SAVEPOINT/backoff loop is application-side by design — sleeping in the DB pins a pooled connection. Required app-harness test: **N=32 concurrent submits against one series ⇒ zero duplicates, zero gaps, ≤6 retries each**, and a *measured* throughput of ≈`1/commit_latency`/s. Assert the number; do not assert "fast". → S1-13.
2. **The migrator writes through the audited chokepoint (§3.5 property 6).** That test is the compliance argument. It lives in the CI acceptance suite, not in a unit file someone can quarantine. → S1-11, RS-F2.
3. **Cross-database denial and header stripping (§3.7).** A wrong connection errors rather than leaks; an inbound `X-Tenant`-shaped header is rejected at the edge *and* by the app. → S1-05.

§7 Stage 3. **Demonstrable:** one continuous story — truck at gate → weighbridge → GRN → RM issue → work order → FG → dispatch with an e-way bill; **and a job-work challan crossing its §143 window and raising an alarm.** This is the demo that closes deals.

#### Lane C2 — Job work: the differentiator

> **Positioning discipline, binding on every engineer, every demo and every sales conversation (§8.2 W2).**
> **india-compliance already ships a `GST Job Work Stock Movement` report.** A maintainer closed a March 2026 request for a job-work-challan report as `not_planned` with *"This report is already available."* ***"ERPNext has nothing here" must stop being said.*** What it does not ship — a repo-wide grep for `143`, `deemed supply`, `one year`, `three year` returns **only HSN-code digit coincidences** — is **a clock**: ageing a challan against the §143 window, posting a deemed-supply invoice dated to the original dispatch, and computing interest from that date.
> **A stock-movement report is not a liability engine. Our differentiation is the liability engine — ageing, deemed supply, ITC reversal — not the register.** The register is the commoditisable half any of hundreds of Frappe partners ships in a quarter, free. That is precisely why J5 moved into v1.
> The liability is **documented, not hypothetical**: *Tvl. Technocast Foundry v. State Tax Officer*, **2026-VIL-582-MAD**, judgment 08.06.2026, upheld extended limitation under **s.74** on *"failure to maintain job-work records, furnish Form GST ITC-04 and establish return of goods within the prescribed period"* — with the job worker a **sister concern**, i.e. exactly how SME job work actually runs. **Sell the liability, not the ITC-04 filing** — the codified filing penalty is capped at ₹25,000 under s.125, and the Madras HC case settles which half bites.
> Demand remains **[PHASE8 UNEVIDENCED]**. Q1's falsification criterion governs whether this ships as an ERP or as a module.

## 5. THE RED CI SUITE

§7 "Continuous, from month 1": *a red CI acceptance suite that produces a GST-valid invoice, a valid e-invoice payload, a delivery challan, a Table 13 extract and a GSTR-1 extract from a seeded company, and asserts T16. It stays red until Stage 2 passes.* §9.3 names it **the single counter-measure to R1**, the register's central risk.

### 5.1 Why it exists from day one, and not from Stage 2

Because its value is that it is **failing while there is still time to change the foundation**. A suite written after Stage 2 tests what was built. A suite written in month 1 tests what was promised, and every month it stays red it names which promise is still unkept. §7 puts the compliance gate at the *definition of done for the foundation*, not in a downstream module — and a suite that only appears once the foundation is finished cannot do that job.

### 5.2 What "stays red" means mechanically

Not aspirational, and not skipped. Three mechanisms:

1. **`packages/acceptance` is a normal Bun test package.** The CI job runs it with `continue-on-error: true` **while the file `packages/acceptance/ACCEPTANCE_MUST_PASS` is absent**. Creating that file — a one-line PR at the end of Stage 2 — flips the job to blocking. **There is no other switch**, no environment variable and no config flag.
2. **A guard test that always runs blocking.** `tests/acceptance/00-suite-integrity.test.ts` fails the build if (a) any test in the package is `.skip`, `.todo` or `.only`; (b) the count of `test(` declarations drops below the number in the committed `MANIFEST.json`; or (c) any assertion file listed in `MANIFEST.json` is missing. **This is what stops the suite being quietly hollowed out to make CI green** — the exact failure mode §9.3 exists to prevent.
3. **Every currently-failing assertion prints why.** `expect()` is wrapped so an unimplemented dependency reports `NOT YET BUILT: <work item id>` rather than a bare diff. **The suite doubles as the Stage-2 burndown**, and the burndown is generated from the test run rather than maintained by hand.

### 5.3 Fixtures — concrete, and built by one entry point

All fixtures live in `packages/testkit/fixtures/` and are built by `seedAcceptanceCompany(db): Promise<AcceptanceWorld>`. **No test constructs its own data.**

**F1 — Company and registrations.** `Shreeji Engineering Works Private Limited`, PAN `AABCS1429R`. Registration A: Maharashtra, state code `27`, plant. Registration B: Gujarat, `24`, depot. `tenant.timezone = Asia/Kolkata`. Fiscal year `FY2026-27`. **Default cost centre `MAIN`** — required because `gl_entry.cost_center_id` is NOT NULL and the constraint must be satisfiable on day one.

### 5.5 Pending blocks — assertions that cannot be finalised yet

### 6.3 Architecture

**The boundary, in one sentence: layout is code, properties are data.** A hand-written screen decides *which fields exist, in what order, in what group, in what tab order*. The merged registry descriptor decides *label, visibility, mandatory-ness, precision*. Extension fields appear only inside a declared `<ExtSlot>`. Nothing else crosses. This is the executable form of §3.2's field-render contract.

**Why this is not a generic renderer — three tiers over one primitive.**

| Tier | Used for | Count | Renderer |
|---|---|---|---|
| 1 — hand-built | all 27 submittable documents, heavy masters, every workbench, every operator surface | ~48 of 70 | hand-written JSX composing `<Field>` |
| 2 — scaffold form | long-tail masters (UOM, Batch, Workstation, Operation, Vehicle, Shift Type, QI Template) | ~9 | `<ScaffoldForm entity>` — default section order from the registry |
| 3 — generic list + CRUD | every entity, always | all | `<EntityList entity>` |

§3.8 permits exactly this and no more: *"generic form renderer for core screens — not built (hand-built React; **the generic renderer is a fallback for extension fields and long-tail masters only**)."* **The load-bearing property: all three tiers render through the same `<Field>`**, so the overlay behaves identically on a hand-built Sales Invoice and a scaffolded Batch master, and there is exactly one place a `property_override` can fail to take effect.

**The descriptor carries `provenance` and it is not optional.** §3.2: *"the 'explain this field' inspector ships in the same PR as the overlay — retrofitting observability onto a multi-table merge is what makes these systems undebuggable at year three."* A validation error must be able to name **which layer** made the field mandatory.

**Merge and cache.** `base registry → field_extension → property_override by layer precedence (core, then tenant)` → one immutable merged descriptor per entity per tenant, cached on `(tenant, registry_build_id, overlay_version)`. The version bump is the invalidation event, published on the Redis client-side-invalidation channel. **No wall-clock TTL** — *"a stale form that silently ignores a mandatory flag is a compliance defect, not a cache miss."* A form in flight when the overlay changes shows a non-dismissible reload banner and **blocks submit**.

**Validation round-trip.** Keystroke → widget local **string** state (never a JS number for money/qty/rate) → blur parses to `Dec` and `commit()`s at field precision → value change re-evaluates `depends_on`/`mandatory_depends_on` locally **via the same compiled AST the server runs** → `fetch_from` batches into one resolve call applied atomically → save/submit posts with an `Idempotency-Key` → a 422 returns `{path, code, message, layer, ruleId}` with paths addressing child rows (`items[3].hsn_code`), rendered inline, naming the layer, linking to the inspector. **The client is a latency optimisation and is never trusted; sharing the compiled AST is what stops the two diverging** — a divergence means a form that lets a user submit something the server refuses, which on a keyboard-first entry screen costs the operator a whole re-key.

**Dry-run preview is a first-class button on every submittable form, not a debug tool** — PHASE2 §5 calls it *"the single best UX idea in the codebase"*, and it ships with U-16 in Stage 2.

**Keyboard-first.** §3.13 makes it an explicit requirement — *"the buyer is an accountant coming off Tally, where everything is keyboard, and a mouse-first form is the first thing they will reject"* — **and specifies no keymap.** A working default is held **as data** in `KeyMapProvider` so a Stage 0 finding changes a table rather than components: `Enter` next field (**Enter never submits a document form — the single most important binding**), `Shift+Enter` previous, `Ctrl+Enter` submit, `Ctrl+S` save draft, `Esc` cancel, **any printable key in a link field opens the picker with no click and no dropdown arrow**, `Tab` from the last cell adds a row, `Ctrl+D` fill down, `Ctrl+V` paste range, `Ctrl+K` palette, `/` focus filter, `j`/`k` row nav. The real map must be recorded **by watching a Tally operator's hands**, in the same Stage 0 visit as Q1/Q19. → **OI-57**

**Number, date and currency presentation is a real gap.** The plan specifies precision everywhere and **never specifies presentation**, and for a buyer coming off Tally this is the first thing noticed. Defaults taken and held in one locale record: **Indian digit grouping** (`1,23,45,678.00`), parentheses for negatives, `₹` prefix, `dd-MM-yyyy` in the **tenant's** timezone, qty trailing zeros trimmed to 3dp minimum, amount in words on the Indian lakh/crore scale. All six are engineering judgement with no source — confirm in Stage 0 by opening a Tally screen, which costs nothing. → **OI-58**

**Report and list shells share one `FilterBar`.** That single component is what makes ~25 reports cost one screen. Scoping filters are **injected by the shell from app-shell context, never declared per report**, because they are NOT NULL scoping columns and the predicate applies them regardless — **a report cannot widen its own scope.**

**Print.** View model → confined Nunjucks → HTML → Chromium in `apps/pdfd` (or the worker on the small profile), never the API. **The Rule 48(5) block is enforced server-side in the render job, independently of the UI** — the disabled button is a courtesy, not the control, because a service-layer guard is not sufficient for a compliance argument. **U-57 evaluates the same block against cached document state when offline and refuses to queue the op** — queuing a forbidden gate-out and failing on replay means the truck has already left.

**Acceptance criteria, all in CI:**

- **AC-F1** — one worked example ships with `<Field>` or the abstraction is untested. It is **Sales Invoice**, exercising a relabelled core field, a hidden core field, a core field made mandatory by a tenant overlay, a precision change, and two extension fields in two different `<ExtSlot>`s.
- **AC-F2** — `property_override(sales_invoice, delivery_date, mandatory, tenant)` makes the field mandatory on the hand-built form, in the scaffold form, in the AG Grid cell editor **and in the server validator, with zero code change**.
- **AC-F3** — AC-F2's inline error names the layer (`tenant`) and links to the inspector showing the provenance chain.
- **AC-F4** — an `overlay_version` bump invalidates every open client within one poll interval; a form in flight **blocks submit** and shows the reload banner. The test asserts submit is refused, not silently retried.
- **AC-F5** — **every Stage 2 and Stage 3 document form is completable end-to-end with no pointing device**, verified by a Playwright run dispatching only keyboard events. A CI gate, not a review item.

### 6.4 Shop-floor surfaces

**What is and is not a tablet — the contradiction §4.1F names, which must not reach a customer.** §8.5 calls weighbridge *"a serial-port read"* while §8.4 answer 7 promises *"no app… a browser on a cheap Android tablet"*, and **those are incompatible**: Chrome on Android has no Web Serial and indicators are RS-232 into a Windows PC. **The tablet story survives for gate entry and the shop floor, where it is true.**

| Surface | Device | Offline | Why |
|---|---|---|---|
| U-57 Gate Entry | Android tablet, browser | **Full** | the gate loses the network |
| U-58 Job Card terminal | Android tablet, browser | **Full** | the shop floor loses the network |
| U-59 Dispatch queue | Android tablet, browser | read-only cache | — |
| U-60 Weighbridge | **Windows PC + signed agent** | agent buffers; browser queues | RS-232. Not a browser capability on Android |

**`OperatorShell` — the shared frame, deliberately not the app shell.** **No module navigation, no breadcrumbs, no workspace switching** — PHASE7 Rank 2's *"I also often lose track of where I started"* is designed out by having nowhere to get lost, and this is the one place the wayfinding evidence converts directly into a design rule. One primary action per screen, bottom-right, the same colour every time. A persistent offline banner and queue tray showing pending count and oldest-pending age. The session is device-bound and long-lived — **a gate operator does not re-authenticate per truck**, and MFA sits on the supervisor role, not the operator.

Legibility rules, defensible from the 12th-pass hiring bar **without asserting a device or language requirement**: touch targets ≥ 48 px (gloves), body text ≥ 18 px, load-bearing numbers ≥ 24 px tabular, contrast ≥ 7:1 (a lit shed defeats 4.5:1 — **engineering judgement, no evidence, OI-59**), **no hover-only affordance anywhere**, numbers and icons lead and text confirms, every string through `t()` with `en-IN` the only value shipped.

**Offline mechanism.** §3.13 states the requirement and supplies no client story; this is it. A service worker caching the app shell and a scoped master snapshot; an IndexedDB `pending_ops` store whose `id` is a **client-generated UUIDv7 that becomes the document id** and doubles as the idempotency key; **ordered replay, one in flight at a time, per device**. The conflict path is explicit — a server rejection (PO closed, period frozen, document cancelled while offline) moves the op to `needs_attention` for a supervisor, **never silently dropped and never auto-retried into a different document**. Hard bounds: queue depth 200 and age 24 h, either breach raising a loud non-dismissible banner, because **a gate entry queued three days is a business problem, not a sync problem**. Snapshot scope is the open PO/DN/DC/challan list, vehicle and transporter masters and the item list for that gate or workstation, refreshed every 60 s while online with the age displayed. **Everything else stays online-only** — no offline for invoices, vouchers, journals, workbenches or reports. This is not a general offline-first product.

**Per-surface criteria.** **AC-G1** a gate-IN completes in ≤6 taps with no keyboard and no scroll at 1280×800 · **AC-G2** with the network cut, 20 consecutive entries queue and all 20 replay producing exactly 20 rows, **and replaying the same batch twice still produces 20** · **AC-G3** a gate-OUT against an un-IRN'd invoice is refused **offline as well**, evaluated against cached state, and **the op is never queued** · **AC-G4** photo capture works on Android Chrome with no permission prompt beyond the file picker · **AC-J1** the job-card timer survives a reload and a 4-hour offline period to within 1 s, because elapsed computes from a **stored monotonic start stamp, not a running interval** · **AC-J2** a downtime entry cannot be saved without a reason code and is always FK'd to the job card, **and no API path exists to create an unlinked one** · **AC-J3** starting on a double-booked workstation is refused **with the conflicting card named**, not a generic error · **AC-J4** scrap always carries a reason code and posts as a taxable-outward-supply candidate, not a silent qty adjustment · **AC-W1** with the agent stopped, the manual path completes a ticket, marks `source='manual'` and **cannot be saved without the photo** · **AC-W2** opening the weighbridge route on Android renders the **manual path only** and says so in one sentence — **this is the guard that stops §8.4 answer 7's contradiction reaching a customer** · **AC-W3** the agent is code-signed and its POST carries an idempotency key · **AC-W4** variance beyond the rule-store tolerance blocks completion and requires a supervisor with a reason.

**Funding gate, restated because §8.2 W3 makes it a condition of the wedge:** if `apps/agent-weighbridge` is not funded, **weighbridge comes out of W3 and out of the sales script.** It does not ship as a manual-only screen while being sold as an integration.

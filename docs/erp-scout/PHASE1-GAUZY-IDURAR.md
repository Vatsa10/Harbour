# Phase 1 ERP Scout Report — Ever Gauzy & IDURAR

**Status: PARTIAL.** This covers two of four planned references. `odoo` and `erpnext` are still cloning and will be scanned in phase 2. Every conclusion here — especially the capability matrix scores and the "adopt this" recommendations for finance, inventory, manufacturing and purchasing — is provisional and expected to be revised downward or replaced once the two mature ERPs are in scope. Neither repo scanned here is a real ERP; treating this report as a design mandate would be a mistake.

Repos scanned:

- `ever-gauzy/` — Ever Gauzy, NestJS + TypeORM/MikroORM monorepo, AGPL-3.0
- `idurar-erp-crm/` — IDURAR, Express + Mongoose monolith, license ambiguous (see §5)

Evidence base: seven deep scans of ever-gauzy (platform, multi-tenancy/security, finance, HR, time-tracking, projects/tasks, inventory/commerce, integrations/AI, frontend) plus one partial scan of idurar's backend. Each scan was adversarially audited; where scout and audit disagreed, the audit is reflected here. **The idurar scan is materially thinner than the gauzy scans** — one backend-only pass, no frontend, no audit of equal depth. Its scores below carry correspondingly lower confidence.

## 1. Verdict per repo

### ever-gauzy

Ever Gauzy is a **multi-tenant SaaS work-management platform** — time tracking, projects/tasks, HR/ATS, and light invoicing — that markets itself as an ERP. Judged as a platform it is genuinely strong: `packages/core/src/lib/core/entities/base.entity.ts` through `tenant-organization-base.entity.ts` bakes a three-level tenancy model (tenant → organization → employee) into the base class so ~300 entities cannot forget it; `packages/core/src/lib/core/crud/tenant-aware-crud.service.ts` force-injects the tenant filter into every read and write; `packages/plugin/src/lib/plugin.ts` gives a ~25-line plugin decorator that lets an external module add tables, ORM subscribers, and even custom columns on *core* entities without forking. The time-tracking domain (`packages/core/src/lib/time-tracking/`) is the most battle-tested code in the repo — the 10-minute `TimeSlot` as atomic unit, the crash-recovery clamp in `timer/timer.service.ts:434`, the stale-timer reaper, and the Electron offline replay queue in `packages/desktop-ui-lib/src/lib/offline-sync/concretes/sequence-queue.ts` represent years of real-world failure absorption. Judged as an **ERP** it is not one: there is no double-entry accounting, no chart of accounts, no journal, no GL posting, no period close; invoice tax and totals are computed **in the Angular client** (`apps/gauzy/src/app/pages/invoices/invoice-add/invoice-add.component.ts:961`) and the API persists whatever the browser posts; multi-currency is a string label with zero FX rate storage anywhere in `packages/core` (verified by grep); "inventory" is a two-table quantity cache (`warehouse-product.entity.ts` → `warehouse-product-variant.entity.ts`) with no stock moves, lots, reservations, valuation, receipts or transfers; there is no manufacturing, no purchasing, no payroll engine, and no overtime rules (grep for `overtime` across `packages/core` returns nothing). Take its platform layer; do not take its business domains.

### IDURAR

IDURAR is a **small invoicing/quoting CRM**, not an ERP, and it does not pretend to be architecturally ambitious. Its entire framework is three glob calls: `backend/src/models/utils/index.js` globs `src/models/appModels/**/*.js`, derives entity/model/controller names from **filename casing**, and emits a `routesList`; `backend/src/routes/appRoutes/appApi.js` loops that list mounting nine fixed routes per entity; `createCRUDController(modelName)` returns nine closures. The actual domain is three models — `backend/src/models/appModels/Client.js`, `Invoice.js`, `Payment.js` — plus PDF generation and settings. There is no accounting, no inventory, no HR, no projects, no multi-tenancy worth the name. What it is genuinely good at is **speed of scaffolding**: dropping a Mongoose model file into a directory produces a working nine-route REST API with no registration step, and any entity can override individual verbs by adding a directory under `appControllers/`. That convention-over-configuration idea is worth one paragraph of thought and nothing more. As a reference for ERP domain modeling it contributes approximately zero; its inclusion in this study is only justified as a floor.

## 3. Patterns worth adopting

## 4. Traps and anti-patterns

### Security holes to not reproduce (gauzy, confirmed by audit)

| Trap                                                                | Location                                                                                                                          | What breaks                                                                                                                                                                                                                                                                             |
| ------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Permission check ignores the caller's role                          | `shared/guards/tenant-permission.guard.ts:78` → `role-permission.service.ts:474-499` (`includeRole` defaults false)        | The guard passes if**any** role in the tenant has the permission. A VIEWER passes where ADMIN holds the right. `PermissionGuard` passes `true` and is correct — so protection depends on which guard a controller happened to stack. Single most serious finding.            |
| Object-criteria update/delete verified in-tenant, executed unscoped | `tenant-aware-crud.service.ts` ~470-480                                                                                         | `update({email:'x@y.com'}, …)` existence-checks against your own row then issues the UPDATE with the raw criteria, rewriting every tenant's matching row. `softDelete` has the identical shape. Only the uuid path is safe by accident.                                            |
| Guards are opt-in per controller                                    | `app/app.module.ts:576-591` registers no global auth/tenant guard                                                               | 18 of 157 controllers carry no`TenantPermissionGuard`; a new controller is unprotected by default. **Invert this: deny by default, opt out explicitly.**                                                                                                                        |
| Permissions baked into the JWT                                      | `request-context.ts` `hasPermission*` re-`verify()`s the bearer token and reads its `permissions` claim; token TTL 86400s | Revocation takes up to a day to affect in-service checks while guards read the DB behind a 5-minute cache — two sources of truth that disagree, plus an HMAC verify per permission check.                                                                                              |
| Feature flag guard is not tenant-aware                              | `shared/guards/feature-flag.guard.ts:41`, `feature.service.ts:47-55`                                                          | Cache key has no tenantId and the check reads the**global** Feature row, ignoring the entire `FeatureOrganization` override table that exists and is seeded.                                                                                                                    |
| API keys grant unscoped tenant-wide access                          | `shared/guards/api-key-auth.guard.ts:44-49`                                                                                     | Injects`{tenantId}` with no role, no employeeId, no permissions — full-tenant read/write with zero RBAC. Scoped keys are mandatory.                                                                                                                                                  |
| `tenantId` nullable everywhere                                    | `tenant-base.entity.ts` (`nullable: true`)                                                                                    | Rows with NULL tenantId are invisible to scoped queries. No DB constraint, no RLS, no composite`(tenantId, id)` keys — isolation is purely application-layer, and several services (`employee.service.ts:129,479,641`) build raw query builders that re-implement scoping by hand. |
| String-interpolated tenant id in SQL                                | `export-import/export/export.service.ts:305`, `import/import.service.ts:88`                                                   | `WHERE "tenantId" = '${tenantId}'` — value from RequestContext, never parameterized.                                                                                                                                                                                                 |
| Manager check omits the caller                                      | `organization-team-employee.service.ts:250-260, 335-346`                                                                        | Proves*a* manager exists on the team, not that the requester is one, then calls `withoutEmployeeFilter()` to bypass row scoping.                                                                                                                                                    |
| Header-value spoof                                                  | `shared/guards/tenant-base.guard.ts:33`                                                                                         | Tests`rawHeaders.includes('tenant-id')`; `rawHeaders` is a flat name/value array, so any header whose *value* is the literal string satisfies it.                                                                                                                                 |
| Plugin isolation is name-based only                                 | `bootstrap/index.ts:452`                                                                                                        | Entity collision detection compares`entity.name` strings; plugins may mutate `config.customFields.<AnyEntity>` with no namespacing or capability boundary.                                                                                                                          |
| MCP server = one identity per process                               | `packages/mcp-server` `AuthManager` singleton                                                                                 | Every tool call executes as the logged-in service account regardless of caller. Safe only as a per-user desktop sidecar. Gauzy's own`ai-chat/tools/mcp-tools.ts:12-26` documents this hazard.                                                                                         |
| Secrets plaintext at rest                                           | `integration-setting/integration-setting.entity.ts` + `.subscriber.ts`                                                        | OAuth tokens and client secrets stored as plain rows; protection is read-time masking, bypassed by any raw query, migration or DB dump. (The subscriber's default-**deny** masking polarity is itself correct and worth copying — it was a fix for GHSA-3rqg-gpm9-gx84.)         |

### Architectural taxes to avoid

- **Two ORMs.** TypeORM + MikroORM + Knex wired simultaneously in a `@Global` `DatabaseModule`. Every entity carries two decorator stacks; `crud.service.ts` is 916 lines of `switch (ormType)`; `statistic.service.ts` is 2,861 lines largely for this reason; the two branches **drift** (`getEmployeeTasks` matches members-OR-teams under MikroORM, members-only under TypeORM). And MikroORM has no migration path — all 290 migrations are TypeORM. Pick one ORM.
- **Three SQL dialects hand-written per migration.** Every file in `database/migrations/` switches on `queryRunner.connection.options.type` into postgres/sqlite/mysql arms — each schema change authored and reviewed three times, 290 files deep. Pick one production dialect.
- **Business math in the client.** The single worst decision in gauzy's finance domain. Tax, discount, totals, `alreadyPaid`, `amountDue` and payment status are all computed in Angular and PUT back. Two clients would produce two different invoices.
- **`update` implemented as `create({...data, id})`.** Used throughout (`task.service.ts`, `invoice.update.handler.ts`). Upsert-by-save reloads and rewrites the whole aggregate including M2M collections, makes partial updates expensive, and makes change-detection for audit approximate.
- **Recalculate-on-every-write.** `timesheet-recalculate.handler.ts:57` runs a full SUM/AVG over a timesheet's slots on every time-log write and every slot merge — i.e. on every desktop ping from every employee. Obvious scaling wall.
- **Read-then-write with no sequence or lock.** Task numbering (`task.service.ts:961` `MAX(number)+1`) and invoice numbering (`getHighestInvoiceNumber()`) both race under concurrency against a unique index. Warehouse quantities are plain read-modify-write saves with no version column — concurrent adjustments silently lose one.
- **Hand-maintained ordered arrays as schema truth.** `export-import/repositories/repositories.service.ts` is 1,860 lines with the comment *"Warning: Changing position here can be FATAL"* — while `getRepositoryRelationsGraph` already computes the FK graph that should derive the order.
- **Silent failure paths.** `tenant.service.ts` wraps six seeding commands in a try/catch that only `console.log`s, and `onboardTenant` doesn't await it — a tenant can be created and returned with none of its defaults. `organization-team-join-request.service.ts:278-283` uses `finally { return {status: OK} }`, swallowing every error. `import.service.ts:145` builds a junction-table INSERT and only `console.log`s it — many-to-many rows export but never import, so the round-trip is lossy. `PluginModule` continues with a possibly-undefined plugin instance after a resolve failure.
- **`console.log` as the logging strategy** throughout timer, slot, guard and task hot paths — including chalk-colored full entity dumps in production handlers, and `console.log(query.getSql())` left in `task.service.ts:601`, `organization-project-module.service.ts:321,455`.
- **Half-dead subsystems.** Full Apollo GraphQL plumbing serving exactly one resolver and two `.gql` files. `packages/ui-config`'s `UiConfigService` is an empty class body. `PaymentSubscriber` is an empty shell. `lockedAt` and `isBilled` columns exist on `Timesheet` and are never written. `trackInventory`, `canBeRented`, `autoApproveShare`, `maxSharePeriod` are stored and never read.
- **Duplicated source of truth.** CORS headers verbatim in three files (`bootstrap/index.ts`, `core.module.ts`, `graphql-helper.ts`) with the GraphQL copy hardcoding `origin:'*', credentials:true`. Theme palette duplicated between `theme.gauzy-dark.ts` and `themes.scss` with a code comment admitting the drift causes real rendering bugs. `ProductVariant.quantity` duplicates warehouse quantities with no reconciliation.
- **No dynamic form engine in the frontend.** `packages/ui-core/shared/src/lib/forms/` is `helpers.ts` plus location/maps widgets. Backend custom fields materialize as columns but nothing renders them. For a tenant-extensible ERP this is the biggest single frontend gap and there is nothing here to copy.
- **`app.module.ts` imports ~180 modules by hand** in one 400-line list with implicit ordering.
- **Naming trap:** `apps/agent` is the Electron *time-tracking* client, not an AI agent.

## 6. Open questions for the owner

**Scope and sequencing**

1. Which ERP domains are actually in scope for v1? Phase 1 found near-zero usable prior art for accounting, inventory, manufacturing, purchasing, sales orders and payroll — meaning those are either built from scratch, taken from erpnext/odoo in phase 2, or cut. The answer changes what phase 2 needs to extract.
2. Is double-entry accounting in v1, or do we ship an operational ERP that posts to an external ledger (Xero/QuickBooks/ERPNext) first? Gauzy shows what "ERP without a ledger" looks like and it is not credible.
3. Where exactly is the CRM/ERP boundary? Twenty owns contacts/deals/pipelines, but the ERP needs a business-partner master (customer *and* vendor: tax id, payment terms, credit limit). Does ERP own that record and CRM reference it, or the reverse? Gauzy conflates them in `organization-contact`, and every finance and inventory decision downstream depends on this answer.
4. Are HR, ATS, and desktop time tracking in scope at all? They are gauzy's best code, and also the parts furthest from ERP core.

**Architecture decisions blocked on your call**

5. One ORM and one production dialect — confirm? (Recommendation: Postgres + one ORM. SQLite-for-dev only if we actually want a desktop/offline variant.)
6. Tenancy model: application-layer scoping as gauzy does it, or Postgres RLS / schema-per-tenant? Gauzy's holes in §4 are all application-layer failures that RLS would have made structurally impossible. This is the single highest-leverage decision in the report and it must be made before any entity is written.
7. Tenant → organization → employee: do we need all three levels, or is tenant → company enough? Gauzy's third level costs real complexity (the whole `employeeId` auto-filter and its bypass machinery).
8. Can a user hold different roles in different organizations? Gauzy cannot — role lives on `User`, tenant-wide. For a group-of-companies ERP this is likely a hard requirement, and retrofitting it is expensive.
9. Permission storage: gauzy materializes ~600 enum members × 8 roles × N tenants ≈ 5,000 rows per tenant at signup. Do we accept per-tenant editable roles at all, and if so, sparse grants or a bitmask?
10. Frontend framework and — separately — do we need a **dynamic form / custom-field rendering engine** in v1? Neither reference has one. If tenants add fields, this is a from-scratch build and should be planned as such, not discovered.
11. Plugin boundary: what may a plugin actually do? Gauzy lets any plugin mutate any core entity's custom fields with no namespace or capability check. Do we want a capability manifest, or is the plugin author trusted?

**Legal / product**

12. What license is our ERP? If AGPL-3.0, the gauzy constraint disappears entirely and this whole analysis gets cheaper. If anything else, §5's clean-room discipline is binding on everyone.
13. Confirm the odoo clone is Community (LGPL-3.0), not Enterprise, before phase 2 scanning starts.
